### auto-code-fixer — LLM 장애 자동 수정 파이프라인

[github.com/yuneast/auto-code-fixer](https://github.com/yuneast/auto-code-fixer) · Python, Claude Code SDK, GitHub API

운영 서버에서 에러가 발생하면 오류 로그를 수신해 레포를 clone하고, LLM이 코드를 분석·수정한 뒤 브랜치·커밋·PR까지 자동으로 올리는 서버입니다.

사람이 로그를 열어보기 전에 수정 PR이 먼저 올라와 있는 상태를 목표로 만들었습니다. 실무(공부선배)에서는 **AWS CloudWatch Logs의 오류를 탐지 트리거로 붙이고, Celery 비동기 큐로 분석 요청을 처리**하도록 연동했습니다. 같은 오류가 반복될 때 알림과 PR이 쏟아지는 문제는 TTL 기반 중복 제거로 막았습니다. → **PHP Fatal Error 대응 공수 90% 절감**

- [선택 근거] Slack 알림만 붙이는 방식(여전히 사람이 수동 처리) · 애플리케이션 내부에 자동화를 넣는 방식(배포와 결합도 상승) 대비, DevOps 전담 인력이 없는 환경에서는 **독립 서버로 분리한 파이프라인**이 운영 부담이 가장 작다고 판단해 채택

### 가나다콜 — 백엔드 단독 (2023.03 ~ 2024.07)

**고소작업차 실시간 배차 서비스** · 기사 2,000명, 일 배차 30~40건 · 백엔드 전체를 혼자 담당

수주 요청이 뜨면 조건에 맞는 기사 여러 명에게 동시에 뿌려지고, 먼저 누른 한 명에게만 배차되는 구조입니다.

**핵심 성과:**

- 하나의 배차 건에 기사 20~30명이 동시에 수주를 눌러 **중복 수락이 발생**했습니다 → Redis 분산 락으로 동시성 제어 → 중복 수락 재발 없음
  - [선택 근거] DB 트랜잭션 락(락 보유 시간 증가, DB 부하) · 낙관적 락(충돌 시 재시도로 기사 쪽 UX 저하) 대비, 이미 쓰던 Redis 인프라를 활용하면서 **ms 단위 TTL 제어**가 가능한 분산 락을 채택
- 차고지 기준으로 알림을 일괄 발송해 무관한 지역 기사에게도 알림이 갔음 → 사용자 실시간 위치 기반 GIS + 반경 설정 구현 → **불필요한 알림 60% 감소**
- 기사 앱이 새 수주를 알려면 주기적으로 서버를 찔러야 했고, 그만큼 배차가 늦게 떴습니다 → **SSE(Server-Sent Events)로 서버에서 기사 앱으로 수주를 밀어주고, 앱이 닫혀 있을 때는 FCM 푸시로 보완** → 새 수주를 즉시 전달
  - [선택 근거] 폴링(지연 + 기사 수에 비례해 요청 증가) · WebSocket(양방향이 필요 없는데 연결 관리 비용 발생) 대비, **서버 → 클라이언트 단방향 푸시만 필요한 요구에 SSE가 가장 단순**해 채택

**주요 업무:**
- 배차 시스템 아키텍처와 매칭 엔진 설계, 주문·배차·정산 도메인 구현 (엔티티 26개, API 66개)
- 백엔드 외에 **기사용 Flutter 앱과 관리자 웹(React)까지** 직접 개발
- JWT + Spring Security 인증, 로그인 실패까지 남기는 감사 로그, SpringDoc 기반 API 문서화

**퇴사 후 유지보수** (2025.12 ~ 2026.03): Python/FastAPI로 돌던 서버를 **Java/Spring Boot로 전면 이관**하고 레거시 7,722줄 제거. 백엔드·관리자·앱을 모노레포로 통합해 Docker Compose + Makefile로 배포를 단일화.

**기술**: Java, Spring Boot, JPA, QueryDSL, MySQL, Redis, SSE, FCM, Flutter, React

- 배포가 수동이라 릴리즈가 지연되고 배포자마다 절차가 달랐음 → GitHub Actions CI/CD 구축, **배포 트리거를 PR 머지로 단일화** → 수동 절차 제거, 특정 담당자 의존 해소
- 홈케어 이커머스가 추가되며 서비스별 로그인이 분리됨 → 쿠키 기반 통합 인증을 **최초 설계**하고 서비스 중단 없이 전환 → 2개 서비스 단일 로그인
- 코드 리뷰 절차가 없고 주니어 2명이 기능을 단독으로 끝내지 못하는 상태 → PR 기반 리뷰 도입 + 멘토링 → **주니어 2명 독립 개발 가능 수준으로 성장**
- 필리핀 현지 입주민이 관리비를 낼 수단이 없었음 → 현지 PG사(DragonPay)를 연동해야 했으나 **REST가 아닌 SOAP/WSDL만 제공** → `zeep`으로 WSDL 클라이언트를 구성하고 SHA1 digest 서명·결제 토큰 발급 흐름을 직접 구현 → 페소 결제 처리
- 역할이 4종(입주민·관리사무소·경비·본사)인데 도메인이 21개로 늘어나며 라우터 등록과 권한 분기가 흩어짐 → 도메인·라우터를 선언만 하면 **`import_module`로 자동 등록되는 구조**와 역할별 라우터 분리 규칙을 세움 → 도메인을 추가해도 진입점 수정 불필요

팀 기술 스택(Python/FastAPI) 선정과 백엔드 아키텍처 설계를 주도했습니다.

**주요 업무:**
- **방문차량 출입 관리** — QR 코드 발급, 경비실 입·출차 처리, 체류시간 산정, 주차비 정산 여부 관리
- **시설 예약**(최다 규모)·**민원 처리**(입주민 접수 → 경비·관리실 처리 3자 흐름)·**관리비 조회/대납**·**택배 수령 알림**·**단지 투표**·**공지/게시판**·**중고 장터**·**부동산 매물**

- JWT + bcrypt 기반 인증, SQLAlchemy 2.0 / Pydantic 2 기반 레이어 구성

**기술**: Python, FastAPI, SQLAlchemy, Pydantic, MySQL, JWT, Docker, GitHub Actions, PHP
